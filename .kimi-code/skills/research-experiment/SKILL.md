每条都对应一次真实事故。违反任何一条，该批实验数据作废重跑。

## 一、跑实验前的四道门

### 门 1：负载强度必须落在有效区间

```
rho = 单请求平均工作量 × 到达率 / 系统总容量
```

- `rho < 0.3`：系统几乎不排队，四种策略差异极小。此时"网络感知没用"是假结论，
  真相是"没跑到有压力的区间"。
- `rho > 0.95`：过饱和，p95 只在测队列排空时间，是另一个问题，必须明确声明。
- 有效区间：`0.3 ≤ rho ≤ 0.9`。

`run_min.py` 会打印 rho。**任何策略对比结果，如果没报 rho，不许写进论文。**

### 门 2：消融必须是严格子集

`NetworkAwareStrategy(w_net=0)` 的结果必须与 `LeastLoad` **逐位相同**。
若不相同，说明实现有 bug，网络项的贡献无法被干净归因。

验证方式：对每个实验组合比较两者的每请求完成时间数组，要求 `np.array_equal` 为真。
不许用"p 值不显著"代替逐位比较。

### 门 3：同种子可复现

同一配置、同一种子跑两次，每请求的 `(node_id, finish)` 序列必须完全一致。
`Random` 用得上种子；`LeastQueue`/`LeastLoad`/`NetworkAware` 是确定性的，
多种子对它们不产生方差。

**推论（重要）**：配对比较里真正的方差来源必须是**负载实现**，
而不是策略内部随机数。若某个策略在 N 个种子下结果完全相同，
继续加种子是浪费算力，必须改为扰动负载（trace 切片、到达抖动）。

### 门 4：模型假设与实测事实分离

每个参数必须能回答"它从哪来"：

| 来源 | 允许的写法 |
|---|---|
| 公开 trace | 可写成数据事实，注明来源与许可 |
| 公开论文的实测值 | 可引用，注明出处 |
| 工程估算 | 必须标注"工程估算"并进入 Threats to Validity |
| 合成/占位 | **严禁**写成 trace 结果 |

当前已知的工程估算：`prefill_coef`、`decode_coef`、`bytes_per_context_token`、
`staleness` 量级、SLO 定义、`compute_rate` 绝对值。

## 二、staleness 必须拆成两条通道

队列状态与链路状态的时间尺度差一个数量级以上：

- 队列状态：服务时间是亚秒到秒级，1 秒前的队列视图已经不可信；
- 链路状态：拥塞/带宽变化是几十秒量级，监控周期通常 10–60 秒。

**用一个 lag 同时控制两者，会让队列陈旧掩盖链路陈旧的真实效应**
（已实测：30 秒队列陈旧让 p95 涨 36 倍，把网络陈旧的效应完全淹没）。
必须用 `staleness_queue` 和 `staleness_network` 分开控制，并报告来源拆分。

补充：`staleness` 只在**时变网络**上是有效因子。
静态网络下链路陈旧精确无效（实测 Δ=0），因此 3 种网络条件里有 2 种的
stale 档是退化 cell，必须在实验设计中说明。

## 三、指标必须能反映调度质量

**deadline / SLO 不许用固定秒数。** 网络代价由节点选择决定，固定 SLO 会让
miss rate 饱和在 0 或 1（已实测饱和到 0.9），失去信息量。

正确做法：`slo_mode="relative"`，把 deadline 定义为
"该请求在最理想节点上的完成时间 × 倍数"，含义是"允许比理论最优慢几倍"。

主指标：p50/p95/p99 端到端完成时间、SLO miss rate、吞吐。
辅助：平均等待、节点利用率、**网络时间占完成时间的比例（net_share）**。

`net_share` 是 RQ1 的自变量，不是可选的辅助指标——收益边界由它决定。

## 五、汇报结果的强制格式

每个结论必须同时给出：

1. **方向**（哪个策略更好）与**效应量**（Cliff's delta），不能只给 p 值；
2. **条件**（哪种负载 × 网络 × 陈旧度组合）；
3. **不确定性**（置信区间或配对检验的 Holm 校正后 p 值）；
4. **适用范围**（不能外推到什么）。

**负结果与零结果必须报告。** 以下三种都是有效发现，必须写进正文：

- NetworkAware 与基线无显著差异；
- NetworkAware 劣化（小传输量下实测 +1.7%）；
- 回退机制无效。

## 六、禁止的写法

- ❌ "NetworkAware 显著优于其他策略" —— 缺少条件、效应量和不确定性
- ❌ 用合成负载的数字描述 Azure trace 的行为
- ❌ 把 `bytes_per_context_token` 当既定事实；它是决定结论形状的一等实验因子
- ❌ 看完结果再调 `w_net` 并报收益；调参必须作为单独消融，权重结果前冻结
- ❌ 用"训练/验证集"话术掩盖结果导向的参数选择
- ❌ 把单节点 kind/k3d 结果包装成生产级集群性能
- ❌ **"首次 / 没人做过 / 首次研究陈旧遥测"**：Aegis（SIGCOMM 2026，已发表）与 NetKV（预印本）
  各自扫过网络侧遥测延迟，结论同为不敏感。正确口径见 `文献/08-竞争定位（2025-2026）.md` §8.1
- ❌ **拿 1 个种子的一张表下结论**。陈旧/拥塞场景下轨迹是混沌的：实测只改**前 2.5% 请求**的决策，
  4000 请求的 p95 就能差 17%。凡是要写进论文的策略对比，一律 ≥10 个种子 + 配对检验
- ❌ 把 per-request 的 p 值当证据（两万请求下必然"显著"）；统计单位是**种子＝独立的负载实现**
- ❌ 用"只报最好的那条臂/那一档参数"代替对照：三种降权规则、每个阈值档位都要进表

## 七、当前已知的模型简化（必须进入 Threats to Validity）

1. 槽位之间**不争抢算力**：4 个槽位各按满速推进，总吞吐线性叠加。
   真实 GPU 并发会互相拖慢 —— 这会**高估**算力。
2. **没有链路排队**：多请求共用一条链路时不互相拖慢。
   —— 这会**低估**高负载下的网络代价，使报告的收益偏保守。
3. 没有 batch 合并效应。
4. 网络状态观测延迟是常数，没有建模"估计误差"与"陈旧"的区分。
5. 节点间链路独立，没有建模共享上行/汇聚链路的相关性。
6. **对齐度（细变量③）在 n>4 时无法造出强配置**：算力按周期 4 循环、链路按节点数铺开，
   可构造的排名相关 ρ 从 ±1.00 收窄到 ±0.24。因此"anti vs aligned 的差随规模变小"里
   有一半是操纵范围收窄的假象；anti 档本身的收益对规模稳健（−57%~−63%）。见 `measure_link_choice.py`。

## 九、工具与操作坑（都真实发生过，照做就行）

1. **后台跑矩阵必须关掉默认超时**：600 s 的默认超时会在大约第 100 个 cell 处把进程杀掉，
   只留下没有 manifest、没有 `p_holm` 的残片（本仓库已发生 3 次）。长任务用
   `disable_timeout=true` 或把超时设到 1800 s 以上。
2. **改策略构造函数的签名后，必须同步改 `run_matrix.make_strategy()` 的参数白名单**：
   白名单里键名写错 = 参数一路走默认值 = **整轮网格静默失效**，而它不报错。
   核对办法：把某个阈值改到极端值，看落盘的 `w_gated_frac` / `describe()` 有没有变。
3. **两条通道的年龄阈值不能等于任何一档 lag**：相等时触发与否由浮点误差决定
   （`now-(now-2.0)` 会算出 `2.0000000000000004`），实测 Δp95 从 0 跳到 +105%。
4. **`analyze.py` 的输出不要接 `head`/`tail`**：SIGPIPE 会打断它，`report.txt` 被截断，
   看起来像"某一节没内容"。
5. **`runs.csv` 只在全部 cell 跑完后才有 manifest 和 `p_holm`**；中断的运行缺这两样是预期行为，
   不要"修复"它（历史产物一律 append-only，异常只标注原因，不删除）。
