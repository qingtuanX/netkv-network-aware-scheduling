## 术语先说明（第一次出现就解释）

| 词 | 人话 |
|---|---|
| 前处理—生成拆分（PD 拆分） | 把一次对话拆成两台机器干：一台先"读题"（前处理），把读出来的记忆交给另一台"写答案"。 |
| KV 缓存 | 上面说的"记忆"。它是模型注意力机制里的键值对，是拆分式服务真正要在两台机器之间搬的东西。 |
| 传没传到 | 我们不看"程序说成功了"，而是看接收端自己报出来的**收到的字节数**大于 0。 |
| 贪婪解码 / temperature=0 | 让模型每次都选最可能的那个词。同一个输入必须得到逐字相同的结果，这样"结果对不对"才有唯一答案。 |
| 兼容哈希 | 两端启动时互相核对"我们的模型、精度、缓存格式是不是一套"的一段校验码；不一致直接连不上。 |
| `/metrics` | vLLM 暴露的一个网页，把运行中的各种计数器（包括"传了多少字节"）打成纯文本，可以直接抓。 |
| 内网带宽 | 同一家云同一个区域内，两台机器之间那条内部线路的速度。它和我们买的"公网带宽"是两回事。 |
| 按量计费 | 用一小时算一小时的钱，随时可释放。 |
| 释放 vs 关机 | **释放**＝把机器删掉、停止收机器的钱（磁盘可能还在收）；**关机**＝机器还在、很多云仍然在收磁盘乃至机器的钱。 |
| attempt（尝试序号） | 同一件事第几次试着做。失败的那次也要留档，不能被后来的成功盖掉。 |
| manifest（清单） | 一次运行的全部前提记录：版本、镜像、模型哈希、种子、时间、退出码。缺了它，数字以后没法复算。 |

### 2.3 模型大小 × 精度 → 显存需求（这是算术，不是实测）

权重占用 ≈ 参数量 × 每参数字节数。fp16 = 2 字节，FP8/INT8 = 1 字节，4-bit ≈ 0.5 字节（含量化开销约 0.6）。

| 模型规模 | fp16 | FP8 / INT8 | 4-bit | 单卡能不能放下（还要留 ~20% 给激活和 KV） | 本轮选择 |
|---|---|---|---|---|---|
| **1.5B** | ~3 GB | ~1.5 GB | ~1 GB | ✅ **24 GB 卡绰绰有余** | ✅ **B1 本轮用这个** |
| **7B** | ~14 GB | ~7 GB | ~4.5 GB | ⚠️ 24 GB 卡塞得下，但**加载峰值约 30 GB**，这台只有 29.7 GB 内存 → 太紧（第一轮就是卡在这） | 第二轮弃用 |
| **14B** | ~28 GB | ~14 GB | ~9 GB | ⚠️ 单张 24 GB 不够；需 **48 GB 单卡**或 **2×24 GB + TP=2** | 次选（要双卡或贵卡） |
| 32B | ~64 GB | ~32 GB | ~20 GB | ❌ 需 2×48 GB（TP=2） | **B1 不建议** |
| 70B | ~140 GB | ~70 GB | ~40 GB | ❌ 需 4×48 GB（TP=4） | **B1 不要** |

> **怎么读**：行是模型大小，列是精度。同一行里数字越小越省显存，但精度越低结果越可能"
> 和单机完整服务对不上"（那会让 4c 检查变复杂）。**B1 的目的是验证链路，不是压榨显存，所以用 fp16 + 1.5B，把变量减到最少。**
>
> **为什么本轮从 7B 换成 1.5B**（三条理由，报告里写的是同一段）：
> ① B1 只验"流程通不通"，**不验性能** —— 模型大小与四件事的结论无关；
> ② 这两台内存只有 29.7 GB，7B 权重 15 GB、加载峰值约 30 GB，**太紧**；
> ③ 公网慢（实测 hf-mirror 1.82 MB/s(A) / 0.66 MB/s(B)），7B 要下 3.5–4 小时，**纯白烧卡时**。
> 1.5B 的 KV 在 4096 token 输入下约 **117 MB**（见 §2.4），**足够证明"传没传过去"**。

### 2.4 每请求要搬多少 KV（选机型和算时间的依据）

```
KV 字节/请求 = 2(K 和 V) × 层数 × KV 头数 × head 维度 × 每元素字节数 × prompt token 数
```

| 模型量级 | 层数 / KV 头数 / head 维度 | fp16 下每 token | 4096 token 的 prompt | 在 8 Gbps 内网上理想耗时 |
|---|---|---|---|---|
| **1.5B（本轮用的）** | 28 / 2 / 128 | ≈ 28 KiB | ≈ **117 MB（112 MiB）** | ≈ 0.15 s |
| 7B 级 | 28 / 4 / 128 | ≈ 57 KiB | ≈ **0.22 GB** | ≈ 0.22 s |
| 32B 级 | 64 / 8 / 128 | ≈ 256 KiB | ≈ **1.0 GB** | ≈ 1.0 s |
| 70B 级 GQA | 80 / 8 / 128 | ≈ 320 KiB | ≈ 1.3 GB | ≈ 1.3 s |

> **1.5B 那一行怎么算出来的（可复核的算术）**：
> `2(K,V) × 28 层 × 2 个 KV 头 × 128 头维度 × 2 B(fp16) = 28,672 B/token`；
> 乘 4096 token = **117,440,512 B ≈ 117.4 MB = 112 MiB**。
> 本轮客户端最长那条 prompt（`p05_rep24`，约 8.9k 字符）按 4 字符/token 约 2220 token
> ⇒ 单请求 KV 约 **62 MB**，与 117 MB 同量级，够用来证明"传没传过去"。

> ⚠️ 上面第一列的结构参数是**按公开模型配置推算的，必须在租到卡之后用两端 `/metrics` 的
> `vllm:cache_config_info`（含 `kv_cache_size_tokens`、`block_size`）核对**，并以核对后的数字为准。
> 第三列与项目仿真里 `bytes_per_context_token = 3.3e5`（≈320 KiB/token，70B GQA）是**同一套算法**，
> 可以互相对照——这是把仿真和真机接上的一个锚点。
>
> **怎么读**：这张表说明两件事：① 1.5B 的 KV 只有一百多 MB、7B 也只有几百 MB，
> **内网带宽 8 Gbps 就够了**，不需要为带宽去买贵机型；② 如果你日后想测"网络传输真的成为瓶颈"，
> 得把 prompt 拉长或把模型放大。

### 2.5 两端必须一致的清单（来自 B0 §6.4/§7.1 的官方兼容性要求）

vLLM 在握手时会做一次**兼容哈希**校验，下面这些**必须完全一致**，否则直接连不上：

| # | 必须一致 | 怎么在 B1 里确认 |
|---|---|---|
| 1 | **vLLM 版本**（精确 tag） + **NIXL 连接器版本** | 两端 `vllm --version` + `pip show nixl`，写进 manifest |
| 2 | **模型**：架构、dtype、KV 头数、head 维度、层数 | 两端对模型目录整体算 sha256 并比对 |
| 3 | **注意力后端（attention backend）** | 启动参数 + 启动日志 |
| 4 | **KV cache dtype**（`cache_dtype`） | 两端 `/metrics` 的 `vllm:cache_config_info` |
| 5 | **投机解码配置**（EAGLE/MTP 等） | **B1 建议全部关掉**，减少变量 |
| 6 | **NIXL 传输模式**：push 还是 pull | 官方原文：两者"use incompatible transfer protocols and **must never be paired**" |

可以不同但有前提的：`tensor-parallel-size`（受模型类型限制）、`block-size`（**只支持 P < D**）、
KV 块数量、`num_speculative_tokens`。
明确不能选的：**Encoder-Decoder 架构 ❌**、**Multimodal ❔（未验证）**、**动态量化 KV ❌**。

官方给了 `enforce_handshake_compat: false` 来关掉校验，原文是 "at your own risk"。
**B1 不要关**——它是我们最便宜的"两端是不是配错了"的哨兵。

> **怎么读**：这张表是"错了会怎么爆"的清单。第 2 条尤其危险：模型形状对得上但权重不同，
> 会**静默传错数据**（不报错，结果错）。所以两端模型目录必须整目录算哈希比对。

### 2.6 KV 指标**怎么读**（这一节最要紧，读错就会把"没发生"当成"发生了"）

**为什么不能提前做完**：B0 已经在本机单实例上抓过 `/metrics`（vLLM 0.31.0，92,703 字节原始快照），
实测 **`nixl` 命中 0 行** —— 因为单实例根本没有 KV 传输。
所以"目标版本上这些指标到底存不存在"**只能在拆分模式下确认**，只能租到卡之后做。

#### 2.6.1 ⚠️ `nixl_bytes_transferred` 是**直方图**，不是计数器

这是最容易搞错、也最容易出假结论的一条。Prometheus 的**直方图（histogram）**在 `/metrics` 里
会展开成三条以上的时间序列：

```
vllm:nixl_bytes_transferred_bucket{le="...+Inf", ...}   ← 分桶累计（这次传输落在哪个大小档）
vllm:nixl_bytes_transferred_count{...}                  ← 样本数
vllm:nixl_bytes_transferred_sum{...}                    ← 观测值总和（字节）
```

**官方说明：样本按「通知次数」统计，不等于请求次数。** 所以：

| 量 | 它真正的意思 | **它不是什么** |
|---|---|---|
| `_count` 的增量 | 发生了多少次「KV 传输通知」 | ❌ 请求数 |
| `_sum` 的增量 | 一共搬了多少**字节** | ——（这就是证据） |
| `_bucket` 的增量 | 这些传输的大小分布 | ❌ 请求数 |

**因此验收必须做到四条**（缺任何一条都不算证据）：

1. **比较运行前后的「样本数」与「字节总和」的变化** —— 不能只看"指标名出现过"。
   进程一起来名字就有了，值可能全是 0；"名字出现过"**证明不了任何传输发生过**。
2. **保留全部标签（label）**，不能只留指标名 —— 同一族可能有多条序列（不同 `engine` / `model_name` / `le`），
   只汇总一个数会把"某条序列没动"掩盖掉。
3. **落盘原始文本**（`/metrics` 正文原样存，不加工），便于日后复核。
4. **前处理端与生成端都要抓** —— 一端抓到不能替另一端作证。

**实现**：`sim/k8s_test/b1_metrics_delta.py`（只依赖标准库）做 1–3；
`run_b1.sh` 的 `grab_metrics()` 做 3（原样存 `metrics_*_raw.txt`）、`mdelta()` 对**两端各跑一次**。

**判据（三选一，互斥）**：

| 判读 | 含义 | 处置 |
|---|---|---|
| **有增量** | `_count` 和/或 `_sum` 变大了 | ✅ 传输确实发生过（这就是 4b 的正证据） |
| **出现但未动** | 名字都在，样本数与字节总和一点没变 | ❌ **不能**判"KV 已传到"：要么没触发，要么快照取早了/取错了端点 |
| **未出现** | 两次快照里一条都没有 | 这**不是「传输量为 0」**，而是「这个版本里没有这一项」→ 走停止条件 S2 |

**要确认存在的指标**（B0 §3 列的清单，逐条对照）：

- `vllm:nixl_bytes_transferred` ← **最重要的一个**（"传没传到"就靠它的 `_sum` 增量）
- `vllm:nixl_xfer_time_seconds`、`vllm:nixl_post_time_seconds`
- `vllm:nixl_num_descriptors`
- `vllm:nixl_num_failed_transfers`、`vllm:nixl_num_failed_notifications`
- `vllm:nixl_num_kv_expired_reqs`、`vllm:nixl_num_notifications_after_expiry`
- `vllm:prompt_tokens_by_source_total{source="external_kv_transfer"}`（B0 实测它**存在**，但在单实例上值为 0.0）

**判据**：如果拆起来之后这些名字**一个都没有**，**先停**（见 §6 停止条件 S2），不要开始测量。
可能的原因：版本里改了名、需要开某个开关、连接器没生效。**这一步失败了不算"B1 失败"，算"还没开测"。**

### 2.7 三样东西**不许混为一谈**（写报告时逐条对照）

| 东西 | 它是什么 | **不能**当什么 |
|---|---|---|
| `kv_cache_size_tokens`（`vllm:cache_config_info` 里） | **缓存容量信息**（这台机器最多能装多少 token 的 KV） | ❌ 某次请求**实际传过去**的字节 |
| 理论 KV 估算（见 §2.4 的算式） | 量级参考，用公开模型配置推算 | ❌ 实测传输量 |
| 显存占用（`nvidia-smi`） | 资源消耗 | ❌ 传输量 |

**Qwen2.5-1.5B-Instruct 的理论 KV 供对照**（28 层 / **2** KV 头 / head 维度 128；FP16、K/V 两份）：
**4096 输入 token ≈ 117.4 MB（112 MiB）**。**这只是理论量级**；**实测必须用连接器记录核对**，
不许把理论值或显存容量冒充实测传输量。

> （上一轮用的 Qwen2.5-7B-Instruct 是 28 层 / 4 KV 头，同一算法给出 4096 token ≈ 224 MiB ——
>  本轮换成 1.5B 后这个数**不再适用**，两者不要混着引用。）

> **怎么读**：这三行是三种完全不同的东西，但它们在报告里长得都像"KV 有多大"。
> 一旦混用，就会写出"我们观测到传了 224 MiB"这种**没有任何证据支持**的句子。

### 2.8 指标拿不到时，备用证据要**具体**

**通用网卡字节数不能当 KV 字节数**（含包头、含 SSH 与 pip 等其它流量，会把不相干的东西算进来）。

若 NIXL 指标拿不到，按下面的顺序退：

1. 用**能明确记录「KV 接收端实际收到多少字节」的连接器日志或接收侧计数**
   （例如生成端连接器自报的收到字节、或 `vllm:prompt_tokens_by_source{source="external_kv_transfer"}`
   这类**明确指向外部 KV**的计数器，而不是网卡计数器）；
2. **还拿不到 → 停在工具/配置排查，不准判「KV 已传到」。**
   按停止条件 S1/S2 处理：把卡在哪一步、报错原文写清楚，结论写成"未验证到"。

### 2.9 内网这件事，**ping 不够**

**低延迟 ping 只是好迹象，不能证明 NIXL 的 KV 数据走了内网。** 开正式请求前必须做三件事：

| # | 要做的事 | 判据 |
|---|---|---|
| 1 | 确认**厂商、地域、可用区、私有网络、子网** | 控制台进不去就用**云元数据服务**核实（本方案即用 `http://100.100.100.200/latest/meta-data/`），并在记录里写明**用的是哪种方式**。实测结果见 §2.1 |
| 2 | 核对 **NIXL 的实际连接地址与路由** | `ss -tnp` 看已建立连接的对端地址**是内网 `172.29.31.x` 还是公网 `8.155.x`**；`ip route get <对端内网IP>` 看**走哪张网卡**（应为 `eth0`）、源地址是否为本机内网 IP |
| 3 | 确认**服务端口只对实验内网开放** | `ss -ltnp` 里服务**不应出现 `0.0.0.0`**：P/D/对照臂绑本机内网 IP，代理绑 `127.0.0.1`。并从**外部（本机经真实公网）**尝试连接公网 IP 的端口，**必须连不上** |

**实现**：`run_b1.sh` 的 `netproof()`（第 1–2 项，穿插在 precheck 里）与
`phase_cleanup_check()` 的公网不可达段（第 3 项）。产物：`netproof.txt`、`cleanup_check.txt`。

> **怎么读**：第 1 项回答"我们在哪儿"，第 2 项回答"数据实际怎么走"，第 3 项回答"有没有多暴露"。
> 三项都过，才能说"KV 走的是内网"。**只做第 1 项（或只 ping 一下）就下结论，是不成立的。**

### 3.0 成本口径修正：**「机器已租 ⇒ 增量成本为 0」是错的**

这一节是 2026-10-07 的更正，**必须先读**，否则后面的预算表会被误用。

| 错误想法 | 为什么错 |
|---|---|
| "机器已经租了，继续跑不额外花钱" | **错。** 这两台**正在按小时计费**；**不用重新采购 ≠ 继续运行不收费**。从现在起每一分钟都在产生新费用，越晚释放越贵。 |
| "关掉进程 / 关机就停止计费" | **错。** 至少云盘还在计费；GPU 按量实例通常**关机也继续收机器费**。真正的止损只有**释放（删掉实例）**。 |
| "¥400 是已确认的预算" | **错。** ¥400 是方案里给的一个**建议档位**，**作者没有确认过**。本文件**不把它当作已定的事实**叙述。 |

**按实际计费方式算「从现在开始继续跑」要花多少**：

```
继续运行的费用 = 单价 P(元/卡/小时) × 每台卡数(1) × 台数(2) × 从现在到释放的小时数 H
              = 2 × P × H
```

### 3.3 计费陷阱（**逐条都要在开机前确认，这些都是真实会扣钱的地方**）

| 1 | **停机 ≠ 停止收费** | 多数云"关机"后**云盘继续收费**，有些机型连机器费也照收。B1 的纪律是**释放**（删掉实例），不是关机。 |
| 2 | **"释放"与"关机"是两个按钮** | 只有在"释放/退还/销毁"之后，控制台的实例列表才会清空。**收尾时必须以"实例列表为空"为准**（阶段 A 的收尾就是按这个核对的）。 |
| 3 | **云盘是独立计费项** | 租实例时附带的系统盘/数据盘在部分云上单独计费；AutoDL 更是明确"付费数据盘单独计费…**无论实例是否开机，均会计费**"。 |
| 4 | **按量 vs 包月** | 包月单价看起来便宜，但 B1 是**几小时到一两天**的短任务，包月会被锁住整月。**B1 一律选按量。** |
| 5 | **公网带宽是另一个坑** | 若给实例配了固定带宽，那是**按小时**扣的（0.063 元/Mbps/小时起）。B1 只需要 SSH，建议**只按流量计费**（0.80 元/GB）或干脆走已有公网 IP。 |
| 6 | **流量统计比应用层多约 10%** | 腾讯云官方说明：包头 + 重传会让计费流量比服务器自统计多约 10%。 |
| 7 | **快照会继续收费** | 收尾时如果做过快照，快照容量是单独的计费项，要一起删。 |
| 8 | **GPU 配额可能要单独申请** | 多家云的 GPU 机型有**独立配额**，新账号默认可能是 0，需要提交申请（有的要等审核）。**这一步不提前确认，会在租卡当天卡住。** |
| 9 | **国内 GPU 常常没现货** | 常见情况是"该可用区该机型已售罄"，需要换地域/可用区。**机型和地域要同时准备 2 套备选。** |
| 10 | **镜像与模型存储也要钱** | 镜像按容量计（AutoDL：0.01 元/GB/日，30 GB 内免费）；模型权重十几 GB，如果放进付费存储会按天累积。**跑完立刻删。** |

> **怎么读**：第 1、2 条是**最容易吃亏**的两条——很多人以为点了关机就不花钱了。
> 第 8 条是**最容易卡住流程**的一条，建议在决定租卡的同一天就去提交配额申请。

### 3.4 四档预算方案

**总机时费公式**（B1 是两台单卡机器）：

```
总机时费 ≈ 单价(元/卡/小时) × 每台卡数(1) × 台数(2) × 累计开机小时数 H
        = 2 × 单价 × H
```

**换算表（把你在控制台查到的单价代进来）**——表里的行列**都是假设档位，不是任何厂商的报价**：

| 累计开机 H（每台） | @¥2/卡时 | @¥4 | @¥6 | @¥8 | @¥12 | @¥24 |
|---|---|---|---|---|---|---|
| 2 h | ¥8 | ¥16 | ¥24 | ¥32 | ¥48 | ¥96 |
| 4 h | ¥16 | ¥32 | ¥48 | ¥64 | ¥96 | ¥192 |
| 8 h | ¥32 | ¥64 | ¥96 | ¥128 | ¥192 | ¥384 |
| 16 h | ¥64 | ¥128 | ¥192 | ¥256 | ¥384 | ¥768 |
| 24 h | ¥96 | ¥192 | ¥288 | ¥384 | ¥576 | ¥1,152 |

> **怎么读**：**列头是你查到的单价，行是两台机器一共开着多少小时，交叉点是两台机器的总机时费。**
> B1 的合理 H 是 **6–10 小时**（含装环境、下模型、调连接器、做四项检查），
> 第一次做、且踩坑多的话按 **12–16 小时**留余量。

**四档方案**（预算上限含机时 + 云盘 + 公网 + 存储；不含任何性能测试，因为 B1 不做性能）：

| 档 | 名称 | 目标 | 建议预算上限 | 单次最长运行 | 在 ¥3/卡时 下可跑 | 在 ¥6/卡时 下可跑 | 在 ¥12/卡时 下可跑 | 适合谁 |
|---|---|---|---|---|---|---|---|---|
| **A** | 最小验证 | 只回答 4a–4d，不重跑 | **¥150** | 4 h | 每台 25 h | 每台 12.5 h | 每台 6.3 h | 想先确认"到底能不能跑通" |
| **B** | **保守（推荐起步）** | A + 每项各重跑一次 | **¥400** | 6 h | 每台 66 h | 每台 33 h | 每台 16.7 h | **默认选这个** |
| **C** | 标准 | B + 换一次模型规模或精度 | **¥800** | 8 h | 每台 133 h | 每台 66 h | 每台 33 h | 需要顺便把"换模型还灵不灵"也写清楚 |
| **D** | 宽松 | C + 故障/排队重跑余量 | **¥1,500** | 12 h | 每台 250 h | 每台 125 h | 每台 63 h | 云上排队久、或账号/配额要现申请 |

> **怎么读**：**先选 B**。A 太紧（连一次失败重跑都容不下，而第一次做几乎一定会失败）；
> C/D 只有在你打算一次把多个模型规模也扫掉时才需要。
> "可跑"列是**每台机器**能开的小时数，不是总卡时。

**一个用已核实数字算出来的最小例子**（腾讯云广州，2 台，每台 1 卡，每台挂 40 GiB 高性能云硬盘，按量计费，开 8 小时）：

| 成本项 | 算法 | 金额 |
|---|---|---|
| GPU 机时 | 2 × 单价 × 8 | **16 × 单价**（待填） |
| 云硬盘 | 40 GiB × 0.0009 元/GiB/小时 × 8 h × 2 台 | **¥0.58** |
| 公网（只 SSH，按流量） | 假设合计 3 GB × 0.80 元/GB | **¥2.40** |
| 内网 KV 流量 | 待核实（§3.2 最后一行） | **?** |

> **怎么读**：这个例子说明**云盘和流量在 B1 这个量级上几乎可以忽略**（几块钱），

## 4. 运行与记录规则（**这一节是硬约束，脚本必须照此实现**）

### 4.1 为什么要有这一节

阶段 A 报告（`sim/k8s_test/STAGE_A_PERIOD4.md` §6）发现：批次脚本 `run_stage_a_repeat.sh`
内置了"**正式测量失败后自动重跑**"的分支（`MAX_ATTEMPTS = 4`），
其中至少 6 类作废条件发生在**已经开测之后**（字节不一致、工具无有效读数、`overlimits` 增量 = 0、
整轮增量 ≤ 0、`iperf3` 无读数、并发段超限），**这与"不静默替换失败轮"的规则直接冲突**。

那 50 轮实际**一次都没触发**（作废 0 次、全部 `attempt = 1`），**没有数据被丢弃或替换**；
但"脚本具备静默重跑的能力"这件事本身必须修掉。

**B1 的脚本必须从一开始就按下面的规则写，不得复用 `run_stage_a_repeat.sh` 的重跑分支。**

### 4.2 规则（逐条）

| # | 规则 | 具体做法 |
|---|---|---|
| **R1** | **每次尝试都落盘，并且带 `attempt` 序号** | 产物文件名与每行记录里都有 `run_id` + `attempt`（从 1 开始，只增不减） |
| **R2** | **失败记录不删、不覆盖** | 产物 append-only；新的运行写**新的 `run_id`**，绝不覆盖旧文件；旧的失败尝试目录原样保留 |
| **R3** | **只有"测量前的前置检查未通过"才算"未开测"（可重试）** | 见下表左列。这类重试**仍要留下记录**，但它**不计入正式测量轮的分母** |
| **R4** | **一旦开测，失败就必须留下** | 见下表右列。第一条测量请求发出之后发生的任何失败，**就是最终结果**，不得重跑替换、不得只报成功的那次 |
| **R5** | **汇总时失败轮计入分母** | 例如"5 次尝试里 2 次失败"要写成 **3/5**，不是"3/3 成功"；并列出每次失败的原因 |
| **R6** | **不得复用"作废即重跑"逻辑** | B1 的脚本里不允许出现"检测到失败 → 自动重跑覆盖"的代码路径 |
| **R7** | **每次尝试必须记录的字段** | `run_id`、`attempt`、UTC 起止、退出码、失败原因（自由文本 + 分类码）、两端 vLLM 版本、两端镜像 digest、两端模型 revision 与目录哈希、NIXL 连接器版本、传输模式（push/pull）、注意力后端、`cache_dtype`、实例机型与区域、内网带宽、两端时钟偏差 |
| **R8** | **收尾时必须留下"释放"证据** | 释放后的实例列表（空）、当天账单页导出，一起存进 `results/` |

**前置检查（未开测 → 可重试，但要留记录）**：

| 检查 | 通过判据 |
|---|---|
| 两端进程起来了 | `ss -ltn` 能看到端口在听 |
| 两端版本一致 | `vllm --version` 与镜像 digest 逐字相同 |
| 模型一致 | 两端模型目录 sha256 相同 |
| `/metrics` 抓得到 | HTTP 200 且能 `grep` 到 `vllm:cache_config_info` |
| 兼容哈希握手通过 | 拆分式服务能正常接受第一个请求（不出现握手错误） |
| 时钟同步 | 两端 NTP/chrony 已同步，记录实测偏差 |
| 配额与预算 | GPU 配额已批、预算告警已设 |

**已开测（不可重试 → 失败即留档并停下）**：

| 事件 | 处置 |
|---|---|
| 测量请求返回 5xx / 超时 | 记为失败，计入分母，**停** |
| KV 传输字节数为 0 或与预期严重不符 | 记为失败，计入分母，**停**（走停止条件 S1） |
| 输出与单机完整服务不一致 | 记为失败，计入分母，**停**（S3） |
| 记录缺字段 / manifest 不完整 | 记为失败，**停**（S6） |
| 费用累计达到预算上限的 70% | **停**（S4） |
| 单次运行超过上限小时数 | **停**（S5） |

> **怎么读**：**左右两张表的分界线就是"第一条正式测量请求发出"这个动作。**
> 发出去之前，出问题叫"没开测"，可以修完再来（但记录留着）；
> 发出去之后，出问题叫"这次实验失败了"，必须留在数据里。

### 4.3 4c 的输出对照**要比 token 编号**，不只比显示文本

**为什么**：文本是 token 编号经过后处理（解码、去特殊符、拼空格）之后的产物。
**不同的 token 编号有可能解码成看起来一样的文本**，反过来也一样。
所以"看起来一样"是弱证据；**token 编号逐位相同**才是硬证据。

规则（**必须在正式拆分对照之前写定，不许看到结果之后再放宽**）：

| # | 规则 | 怎么落实 |
|---|---|---|
| 1 | **两端固定同一**：模型修订号、分词器、运行精度、随机种子、生成参数 | 模型：整目录 sha256 两端比对（§2.5 第 2 条）；分词器随模型目录一起哈希；运行精度：从两端启动日志取；`temperature=0`（贪婪）、`seed=0`、`max_tokens` 两端逐字相同 |
| 2 | **先重复几次「单机完整模型」服务，确认基准自身稳定** | `run_b1.sh baseline` 阶段对同一批 prompt **重复 3 次**，把 r1/r2/r3 两两按 token 编号比一遍，结论落 `baseline_stability.txt`。**基准自身不稳，后面「拆分 == 单机」的差异就分不清是谁的错。** |
| 3 | **本规则在跑之前冻结** | 判据写在脚本里（`b1_compare.py` 的 `--baseline/--disagg`），不是看完结果再定 |
| 4 | **区分「权重文件原始精度」与「实际运行精度」** | 官方 Qwen2.5-7B-Instruct 配置标 **bfloat16**。若运行时选了 FP16，**记录里必须把这两个分开写**：原始精度取自 `config.json` 的 `torch_dtype`；实际运行精度取自 vLLM 启动日志 |

**降级规则（必须写明）**：如果某一端没有返回 token 编号（服务没开 `return_token_ids`），
就只能退到按 **显示文本逐字符** 比对。`b1_compare.py` 会在报告顶部**显式写出这是降级证据**，
不允许把降级证据当成"逐 token 相同"来写。

### 4.4 「冒烟请求」与「正式测量请求」的分界（**容易搞混，单独写死**）

| | 安装冒烟检查 | 正式测量请求 |
|---|---|---|
| 什么时候发 | **拆分服务起来之后的第一个请求** | 冒烟通过、进入 `measure` 阶段之后 |
| 发几条 | **1 条** | 先**单请求**，再**少量重复**（每条独立编号） |
| 落在哪 | `attempt{N}/smoke/`（**单独留档**） | `attempt{N}/arm_disagg_r*.json` |
| **算不算正式数据** | **不算** —— 明确**不混进正式请求数据** | **算** |
| 失败了怎么办 | 按 R3 算"**还没开测**"，可以修完重来（记录保留） | 按 R4 **失败即最终结果**，不重跑、不顶替 |
| 它证明什么 | 服务链路**装起来了**、KV 有增量的**首个迹象** | 4a/4b/4c 的正式证据 |

**每次尝试独立编号**：正式臂写成 `disagg_r1`（单请求）、`disagg_r2`…（5 条），
文件名与 `record.csv` 都带 `attempt` 序号。
**任何正式请求失败都保留，不自动重跑覆盖**——`run_stage_a_repeat.sh` 里的
"作废即重跑"分支（`MAX_ATTEMPTS = 4`）**不得复用**（见 §4.1）。

## 6. 停止条件（**触发任何一条就必须停，不许"再跑一次看看"**）

| # | 条件 | 停下后做什么 |
|---|---|---|
| **S1** | KV 传不过去（握手失败，或传输字节数恒为 0） | 停。**不改目标、不换测法**，先修工具/配置，写清卡在哪一步 |
| **S2** | `/metrics` 里 §2.6 的 KV 传输指标一个都没出现 | 停。先确认是不是版本改名/开关没开；**这件事不算 B1 失败，算"还没开测"** |
| **S3** | 4c 输出一致性与单机完整服务对不上 | 停。先排查：权重是否同一 revision、`cache_dtype` 是否一致、注意力后端是否一致 |
| **S4** | 累计花费达到预算上限的 **70%** | 停并拉回产物。**不为"把最后一步跑完"越过预算线** |
| **S5** | 单次连续运行超过上限小时数（默认 6 h） | 停。分段做，不要一次挂很久 |
| **S6** | 记录不完整（缺字段/缺 manifest）却仍在继续测量 | 停。**先修记录再继续**——记不全的运行以后没法复算，等于白花钱 |
| **S7** | 出现"静默错误"信号（例：指标显示未出现却报告成功、字节数对不上、结果看似正常但哈希不同） | 停。静默错误比崩溃危险，必须查清再继续 |
| **S8** | 同一项前置检查连续失败 3 次 | 停，把失败原文与尝试记录整理成一段"卡在哪里"写进报告 |

> **怎么读**：S1–S3 是技术门槛，S4–S5 是钱和时间门槛，S6–S7 是"数据质量"门槛，S8 是"别硬撞"。
> **只要 S1/S2/S3 触发，就说明 B1 的答案已经是"这次没跑通"——这是一个有效结论，不是失败。**
