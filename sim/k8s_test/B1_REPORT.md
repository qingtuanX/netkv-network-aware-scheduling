## 0. 怎么读这份报告（先看这一节，术语都在这里解释）

| 词 | 人话 |
|---|---|
| **拆分式服务 / PD 拆分** | 把一次对话拆成两台机器干：一台先"读题"（前处理），把读出来的记忆交给另一台"写答案"。 |
| **KV 缓存** | 上面说的"记忆"。它是模型注意力里的键值对，是拆分式服务真正要在两台机器之间搬的东西。 |
| **传没传到** | 不看"程序说成功了"，而看**接收端自己报出来的、一共收到了多少字节**，并且这个数在请求前后**变大了**。 |
| **`/metrics`** | vLLM 开的一个网页，把运行中的各种计数器打成纯文本，可以直接抓下来。 |
| **直方图（histogram）** | 一种特殊的计数器。它在 `/metrics` 里展开成三行：`_bucket`（分桶）、`_count`（**样本数**）、`_sum`（**总和**）。**它统计的是"通知次数"，不是请求次数**。 |
| **p95 / 分位数** | "最慢的那一小撮请求有多慢"。 |
| **内网 / 私有网络** | 同一家云同一个区域里，两台机器之间那条不走公网的内部线路。 |
| **冒烟检查** | 正式测之前先发一条请求，确认"装起来了"。它**不算正式数据**。 |
| **门 / 判据** | 开工前的体检项，不过就不许写进论文。 |
| **释放 vs 关机** | **释放**＝把机器删掉、停止收机器费；**关机**＝机器还在，很多云仍然继续收钱（尤其云盘）。 |

## 3. `/metrics` 两端实测结果 —— ❌ **两端都没有抓到（服务从未启动）**

**必须照实写**：本轮**没有**任何 `/metrics` 快照。因此：

| 产物 | 状态 |
|---|---|
| `metrics_precheck_prefill_t0_raw.txt` 等 8 份快照 | ❌ 不存在 |
| `kv_delta_smoke_{A,B}.txt` | ❌ 不存在 |
| `kv_delta_measure_{A,B}.txt` | ❌ 不存在 |

**为什么要把这一条单独写成一节**：因为这正是最容易造假、也最容易读错的地方。
**"没抓到"和"抓到了但是 0"和"抓到了且有增量"是三件完全不同的事**：

| 情况 | 能不能说"KV 传到了" |
|---|---|
| 抓不到 `/metrics`（服务没起来） | **不能**，且**不能**说成"传输量为 0" —— 是"没测" |
| 抓到，但没有 nixl 指标 | **不能** —— 是"这个版本里没有这一项"（→ 停止条件 S2） |
| 抓到，nixl 指标在，但 `_count`/`_sum` 没变 | **不能** —— 出现 ≠ 发生 |
| 抓到，`_count` 与 `_sum` 都变大 | **可以** —— 这才是证据 |

**三样东西不许混为一谈**（报告里如果出现这几个数，必须对号入座）：

| 东西 | 它是什么 | **不能**当什么 |
|---|---|---|
| `kv_cache_size_tokens` | 缓存**容量**信息（最多装多少） | ❌ 某次请求实际传的字节 |
| 理论 KV 估算（Qwen2.5-7B：4096 token ≈ 224 MiB） | 量级参考 | ❌ 实测传输量 |
| 显存占用（`nvidia-smi`） | 资源消耗 | ❌ 传输量 |

**备用证据的选择**（恢复后如果 NIXL 指标拿不到时用）：**通用网卡字节数不能当 KV 字节数**
（含包头、含 SSH 与下载流量）。要退就退到"能明确记录 **KV 接收端实际收到多少字节**"的连接器日志
或接收侧计数；**再拿不到就停在工具/配置排查，不准判"KV 已传到"**。

## 7. 费用口径与上限（**这一节必须和正文一样被认真对待**）

### 7.1 "机器已租 ⇒ 增量成本为 0" 是错的

两台**一直在计费**。继续跑就是继续花钱；**不用重新采购 ≠ 继续运行不收费**。

```
继续运行的费用 = 单价 P(元/卡/小时) × 2 台 × 从现在到释放的小时数 H
```

### 7.2 查到的与没查到的

| 要查的项 | 状态 | 原因 |
|---|---|---|
| 计费方式（按量 / 包月） | ❌ **未查到** | 云元数据服务不暴露；无 `aliyun` CLI；无 RAM 角色（`…/meta-data/ram/security-credentials/` 返回 404） |
| 单价 P | ❌ **未查到** | 阿里云定价页 JS 渲染且需登录；帮助中心全站 0 处"元" |
| 实时账单 | ❌ **未查到** | 需控制台会话 |

→ **本报告不编单价**。金额写成公式；**能不能跑由「时间上限」决定**。

### 7.3 上限（硬约束，已写进脚本 `budget_gate()`）

| 项 | 上限 |
|---|---|
| 单次连续运行 | **4 小时/台** |
| B1 累计 | **16 卡时**（= 2 台 × 8 小时） |
| 金额 | `≤ 16 × P`（P 未查到）；**若** P ≤ ¥25，**则** ≤ ¥400（纯算术，**不代表 ¥400 是已确认预算**） |

> **¥400 的口径**：它只是方案里给的**一个建议档位**，**作者没有确认过**。
> 本报告**不把它当作已定预算**。

### 7.4 本轮实测到的、会直接推高成本的一件事

**这两台的公网入口带宽只有约 0.6–1.2 MB/s**：

| 源 | 实测 |
|---|---|
| `hf-mirror.com` | 0.89 MB/s |
| `modelscope.cn` | 0.87 MB/s |
| `mirrors.aliyun.com` | 0.61 MB/s |
| 同一分片 **8 路并行** | 合计 ≈0.58 MB/s（**比单流更低** ⇒ 瓶颈在实例侧） |
| `mirrors.cloud.aliyuncs.com`（**内网**镜像） | **≈17 MB/s** |

后果：15.2 GB 的 7B 模型要下 **约 3.5–4 小时**，**这段时间两台都在计费**。
**B2 及以后必须先解决带宽（控制台升配）或重新掂量模型大小。**
