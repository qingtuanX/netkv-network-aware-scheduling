## 0. C 只回答三个问题

1. **两家云之间能不能双向传真实 KV**（阿里云→腾讯云、腾讯云→阿里云）？
2. **两个方向是否都能完成请求**（固定 64 词、失败率多少）？
3. **跨云传输量、失败数、首字等待比同云增加多少**（对照 B2 拆分臂）？

## 2. 拓扑与两个方向（一台腾讯云轮流当两角）

| 方向 | 前处理（kv_producer） | 生成（kv_consumer） | 客户端 |
|---|---|---|---|
| **D1 阿里→腾讯** | 阿里云 A10 | 腾讯云 A10 | 前处理机 |
| **D2 腾讯→阿里** | 腾讯云 A10 | 阿里云 A10 | 前处理机 |

- 服务参数与 B2 **完全一致**（`--generation-config vllm --dtype bfloat16
  --no-enable-prefix-caching`，无概率记录设置；nixl kv_producer/kv_consumer）。
- **先做单机健康和配置核对**（腾讯云机器）：vLLM/nixl/模型版本与阿里云一致
  （版本号 + sha256 记录）、单机冒烟通过，才开始跨方向测量。

## 3. 隧道与安全（计划书 §5 明文，不打折）

- **WireGuard 是 NIXL/KV 正式数据通道的首选**。理由：NIXL 要两端互相发现并建立
  数据连接，可能自报私网地址、握手端口与数据端口不止一个、方向切换时连接方向也变
  ——单条 `ssh -L` 端口转发未必承载得住。**安装、密钥、路由、端口连通性必须在
  正式采数前完成并做空载连通检查**，不把安装调试留到计费运行中。
- **`ssh -L` 降为辅助通道**：只用于 HTTP 服务、代理与管理端口。
  **若实测证明 NIXL 能通过固定的 SSH 转发端口双向工作**，才记录为本轮实际方案
  （照实记，不预设）。
- 管理端口（SSH）**只允许指定登录地址**。
- 测试输入一律**合成文本**（沿用 v2 题库）；日志不得含密钥/认证信息/真实用户文本。
- 公网流量费计入预算对账。

## 4b. Q3 解释边界（冻结；写论文照抄）

**两个方向的客户端位置不同**：D1 的客户端在阿里云（前处理机），D2 的客户端在腾讯云
（前处理机）。因此跨云方向的首字等待里可能混入：客户端到前处理端的路径差异、
客户端到代理的路径差异、隧道（WireGuard）开销、两家云公网出口的差异。
**不得把与 B2 同云基线的差值完全归因于跨云 KV 传输**——只能报
"跨云方向记录到的首字等待和总耗时是多少，以及相对 B2 同云拆分基线变化多少"（描述性）。

## 4. 测量内容（对应三问；工具沿用 `b2_perf_client.py` v2.1，不改）

| 问 | 测什么 | 判据 |
|---|---|---|
| Q1 KV 通不通 | 每方向 /metrics t0→t1：nixl 字节/次数/失败、`external_kv_transfer`、本地重算=0 | **可执行判据（冻结）**：① 字节÷token 落在 B2 实测基准 **28,799 的 ±1% 内**；② 传输次数与有效请求数一致；③ 失败传输、失败通知、KV 过期**全为 0**；④ 接收端本地重算 = 0。四项全满足 ⇒ 通过<br>（名词说明：**token = 模型切分文字后的片段**，不一定等于一个汉字或一个英文单词） |
| Q2 能不能完成 | 每方向 5 题 × 10 重复 × {串行 1, 并发 4} = **100 条/方向**（算式 5×10×2 档；两方向共 **200 条**正式，不为凑数加重复）；固定 64 词、token ID 严格模式、失败保留不重试 | 两方向都完成且失败率如实记录 ⇒ 通过（失败率高则照实写） |
| Q3 增加多少 | 每方向的首字等待、总耗时、传输量、失败数；与 **B2 同云拆分臂**做**描述性对照** | 只说"跨云方向记录到的首字等待/总耗时是多少、相对 B2 同云拆分基线变化多少"；**不得把差值完全归因于跨云 KV 传输**（见 §4b 解释边界） |

- 冒烟与热身照 B2 老规矩（冒烟 1 条/会话、热身 10 条/会话，不进统计）。
- 题序：沿用冻结题序文件（每方向用 r1，两方向同序可比）。
- 每方向各 1 个测量会话；**单次连续运行 ≤4h** 包含两方向（预计 1–2h）。

## 5. 统计口径（与 B2 同，收紧）

- C 的单位是"方向"（n=2），只做**描述性**报告：中位 + 范围 + 失败计数；
  **不写**置信区间、不写显著性、不写"跨云性能提升/下降"这类结论。
- 与 B2 的对照只说"**首字等待比同云拆分增加 X（描述性）**"。

## 6. 判定与产物

- `decision.json`：Q1/Q2/Q3 各给 **通过 / 失败 / 未测**；费用对账（单价×时长+流量费）。
- **进 D 判据**：两方向 Q1+Q2 均通过、预算与单价记录齐全 ⇒ 可议进 D；
  任一方向 KV 传输失败/账目异常 ⇒ 停，如实报告负结果收口。
- 产物：`sim/results/c/<run_id>/`（每请求明细 + metrics t0/t1 + record.csv + decision.json）。

## 7. 明确不做（防跑偏）

不测大规模吞吐、不测多模型、不换 7B、不做最终收益结论、
**不把一次跨云可行性试跑写成"跨云性能提升"**。D 才做正式比较。

## 8. 执行顺序（作者冻结的顺序，不改）

```
① 冻结 C_PREREG（作者批准）
② 控制台记录腾讯云四项价格（GPU/云盘/带宽/公网流量）→ record

⑨ 拉取证据

```
