## 0. 一句话结论

**阶段 A 的四条通过条件全部达标，可以进入租 GPU 云的阶段**——但**只在"两台主机、网络命名空间 + 内核 `tc`"这条路径上**。
单机自足模式（电池自带 worker、走回环）只能验前两条，A3/A4 必然不合格，这是设计如此，不是缺陷。

关于术语：**网络命名空间（network namespace）**＝在同一台 Linux 里造出一个"独立的网络栈"，
有自己的网卡、路由和防火墙，看起来就像另一台机器；**`tc`**＝Linux 用来控制网卡排队与限速的工具；
**`overlimits`**＝`tc` 的计数器，记录"因为超出速率而被拦下来排队的包数"，它不为 0 才说明限速真的在起作用。

## 2. 跑了哪条路径、什么机器

| 项 | 值 |
|---|---|
| 路径 1（主要证据） | **WSL2 里的 network namespace 造第二台"主机"**（`MULTIHOST.md` §1.1 那条路） |
| 路径 2（补充证据） | **WSL2 ↔ Windows 主机**：两端在**不同的网络栈**上，走 Hyper-V 虚拟网卡 |
| 内核 | `6.18.33.2-microsoft-standard-WSL2`（Ubuntu 26.04，cgroup v2，16 逻辑 CPU） |
| Python | WSL 侧 `python3 3.14.4`；Windows 侧 `sim/.venv` = Python 3.12.10 |
| `iperf3` | WSL 侧 3.20-2（本机原先未装，本次新装；Windows 侧没有，见 §6） |
| 网卡 | 路径 1：`vethB`（hostB 命名空间内）；路径 2：`eth0`（WSL 侧） |

### 路径 1 的拓扑与 `tc` 参数原文

```text
root 命名空间   10.250.0.1  ── veth0 ─╮   ← 服务端跑在这里（root 命名空间）
                                       ├─ 实验数据流只走这一段
hostB 命名空间  10.250.0.2  ── vethB ─╯   ← 客户端/验证电池跑在这里

root 侧： tc qdisc add dev veth0 root handle 10: tbf rate 25mbit burst 64kb latency 50ms
hostB 侧：tc qdisc add dev vethB root handle 10: tbf rate 25mbit burst 64kb latency 50ms
```

两侧都加，是为了让**上传和下载两个方向都被限速**，否则 A2 只能判定一个方向。
重建这套环境的脚本是 `sim/k8s_test/setup_netns_tc.sh up 25`（幂等，`down` 拆掉，`show` 看现状）。

**"真的被限速"的对照**（否则"限速生效"与"链路本来就慢"分不开）：

| 链路状态 | 同一段 veth 上的实测吞吐 |
|---|---|
| 不加 `tc`（原始 socket 打流 4 s） | **33,577 Mbit/s** |
| 不加 `tc`（`iperf3` 打流 5 s） | **25,914 Mbit/s** |
| 加 `tbf rate 25mbit` 后 | **23.9–24.1 Mbit/s** |

差三个数量级 ⇒ 那个 24 Mbit/s 确实是整形器掐出来的，不是链路能力。

> 顺带复核了 `MULTIHOST.md` §1.2 的第 1 条坑：**同一台机器上两个普通 IP 之间的流量不走 `veth`，
> 会完全绕过 `tc`**。必须有一端在命名空间里。本次严格照做。

## 3. 逐项实测明细

### 3.1 字节一致性（A1）——交付版 `transfer_20261006T031214Z`

| 档位 | 客户端发出 | 服务端声明收到 | 服务端**实际**读到 | 客户端实际收到 | 载荷 CRC |
|---|---|---|---|---|---|
| 0.5 MB | 500,000 B | 500,000 B | 500,000 B | 500,000 B | 两侧一致 |
| 8 MB | 8,000,000 B | 8,000,000 B | 8,000,000 B | 8,000,000 B | 两侧一致 |
| 200 MB | 200,000,000 B | 200,000,000 B | 200,000,000 B | 200,000,000 B | 两侧一致 |

"服务端实际读到"这一列是**按 256 KiB 分块累加真实读到的字节数**得出的，
不是抄 `Content-Length`——抄头部等于什么都没验。载荷内容还比了 CRC32，排除"读到的是上一轮残留"。
另外三次重复（第一、二、三）三档数字**逐字节相同**。

### 3.2 阶段时间分解（A1 附带）——交付版

| 档位 | 入口（建连+组请求头） | 上传 | 服务端段（读余下载荷+算力） | 下传 | 端到端 | 四段之和 − 端到端 |
|---|---|---|---|---|---|---|
| 0.5 MB | 0.004 s | 0.004 s | 0.144 s | 0.147 s | 0.297 s | **0.000000000 s** |
| 8 MB | 0.002 s | 2.301 s | 0.355 s | 2.656 s | 5.315 s | **0.000000000 s** |
| 200 MB | 0.039 s | 66.505 s | 0.392 s | 66.897 s | 133.832 s | **0.000000000 s** |

四段之和恒等于端到端（同一次连续计时切出来的，是恒等式，用来防止"漏记了一段"）。
真正有信息量的是**服务端能自证的账**：200 MB 时客户端 133.832 s − 服务端三段 133.793 s
= **0.039 s 残差（0.0%）**，这点残差是 TCP 握手、首字节传播、响应头与两端计时边界。

> 读法提醒：上传 66.5 s 而"服务端段"只有 0.39 s，是因为客户端 `sendall` 一返回就
> 记"上传结束"——那时数据只进了内核发送缓冲。**真正"对面收完"的时刻由服务端报**，
> 所以吞吐一律用服务端的字节数除以服务端的接收时长来算（否则会系统性高估）。

### 3.3 限速吞吐（A2）与两种独立测法的交叉确认

| 测法 | 上传方向 | 下传方向 |
|---|---|---|
| 应用自身（第一重复） | 24.099 Mbit/s（−3.61%） | 24.096 Mbit/s（−3.62%） |
| 应用自身（第二重复） | 24.099 Mbit/s（−3.60%） | 24.097 Mbit/s（−3.61%） |
| 应用自身（第三重复） | 24.098 Mbit/s（−3.61%） | 24.098 Mbit/s（−3.61%） |
| 应用自身（**交付版**） | 24.098 Mbit/s（−3.61%） | 24.098 Mbit/s（−3.61%） |
| `iperf3`（接收端读数） | 23.9 Mbit/s | 23.9 Mbit/s（`-R`） |
| **设定值** | **25 Mbit/s** | **25 Mbit/s** |

两种互相独立的工具差 **0.8%**，都落在 ±10% 内。
（`iperf3` 报的"发送端 25.0 Mbit/s"是它自己的发送速率；接收端读数才是真的过线速率，
两者差 4.4% 正好是 TCP/IP 头开销。）

### 3.4 `tc` 统计（A3）

```
运行前：qdisc tbf 10: root rate 25Mbit burst 64Kb lat 50ms
        Sent 222872294 bytes 217750 pkt (dropped 0, overlimits 289756 requeues 0)
运行后：Sent 231250123 bytes 223471 pkt (dropped 0, overlimits 300576 requeues 0)
                                        ↑ overlimits +11201
```

`overlimits` 大增说明整形器真的把包拦下来排过队。
整轮跑完（含 200 MB 档）累计见到 `dropped 46`（占 249,294 个包里的 0.018%），
TCP 全部重传补上，对结论无影响，但**照实记下来**。

### 3.5 单路 vs 多路（A4）

| 重复 | 1 路吞吐 | 3 路并发时**每路**吞吐 | 每路下降比值 | 3 路**合计** |
|---|---|---|---|---|
| 第一重复 | 24.101 Mbit/s | 9.469 Mbit/s | **2.55×** | 28.406 Mbit/s |
| 第二重复 | 24.098 Mbit/s | 10.442 Mbit/s | **2.31×** | 31.327 Mbit/s |
| 第三重复 | 24.097 Mbit/s | 8.619 Mbit/s | **2.80×** | 25.856 Mbit/s |
| **交付版** | 24.098 Mbit/s | 11.257 Mbit/s | **2.14×** | 33.770 Mbit/s |

共享瓶颈下"每路"应该降到约 1/3、**合计应基本不变**——实测合计在 **25.9–33.8** 之间波动
（设定值 25）。低于设定值的那次只有 25.9（基本贴住），高于设定值的几次最多到 33.8（+35%），
原因是 **tbf 的令牌桶对每一路新连接都有一段突发额度**：3 路同时开始，就有 3 份突发额度叠加。
每路比值的范围是 **2.14–2.80×**，判据取 ≥1.5（理想值 3），四次全部远高于判据。
第二、三、交付版还记了每请求端到端时间：2.805 → 6.929 s（2.47×）、2.805 → 7.662 s（2.73×）、
2.805 → 6.362 s（2.27×），与吞吐口径同向。

**四次重复都在同一档设定值下得到 −3.6% 的偏差、`overlimits` 都在 +11,200 附近、
每路比值都在 2.1–2.8× —— 这说明阶段 A 的结论不靠单次运气。**
唯一波动较大的是"3 路合计"（25.9–33.8 Mbit/s），已在上面给出原因（令牌桶突发额度），
**不要在论文里把"合计≈设定值"当结论引用**。

### 3.6 网卡计数器 vs 应用层字节（A5，只报告）

| 方向 | 网卡计数器增量 | 应用层字节 | 比值 |
|---|---|---|---|
| `vethB` tx（上传） | +8,367,335 B | 8,000,000 B | **1.0459×** |
| `vethB` rx（下传） | +8,367,458 B | 8,000,000 B | **1.0459×** |

≈ 4.6% 的超出就是 TCP/IP 头（每段 20+20 字节 + 链路层 14 字节，8 MB 约 5,500 段 → 约 298 KB，
与实际相符；差额来自重传与分块边界）。

**⚠️ 这条比值不能当"通用 TCP 开销"用**：换到 WSL `eth0` → Windows 那条路径上，
同样的 8 MB 上传比值只有 **1.0016×**。原因是虚拟网卡开了 TSDO/GSO 之类的分段卸载，
内核计数器数的"包"比真实线路上的帧少得多。**写正文只能用"同一条链路上前后对比"，不能跨网卡比。**

### 3.7 顺带回归：调度器那条路（`client` 角色）也换成了真实字节

阶段 A 的改动会连带影响原有的调度网格，所以单独确认了一次（产物在

## 4. 路径 2（WSL2 ↔ Windows）实测

两端在**不同的网络栈**上（WSL2 是 NAT 模式：WSL `eth0` = 172.24.198.206，
Windows 侧 `vEthernet (WSL)` = 172.24.192.1），走 Hyper-V 虚拟网卡。

| 方向 | 谁跑电池 | 产物 | 结果 |
|---|---|---|---|
| WSL（客户端/电池）→ Windows（服务端） | WSL | `transfer_20261006T030328Z` | A1 三档字节全对 + CRC 一致；A2 上传 **24.043** Mbit/s（−3.83%，`tc` 加在 WSL `eth0` 上）；A3 `overlimits` **+563**；A4 **23.970 → 8.002**，**3.00×**，合计 24.005；A5 tx 1.0016× / rx 1.0481×。**PASS 8 / FAIL 0** |
| Windows（客户端/电池）→ WSL（服务端） | Windows | `transfer_20261006T030624Z` | A1 0.5/8 MB 字节全对 + CRC 一致，四段之和 − 端到端 = **0.000000000 s**；A2 上传 512.2 / 下传 2754.2 Mbit/s（无 `tc`，只报告）；A3/A5 记 n/a（Windows 没有 `/sys/class/net` 计数器、也没有 `tc`）；A4 **FAIL**（Windows 侧没有整形器 ⇒ 没有共享瓶颈可分，与单机模式同理） |

**路径 2 的意义**：它证明这套协议在**两种操作系统、两套网络栈**之间也能逐字节对上，
而不是只在 Linux 回环/同一内核里自证。

**路径 2 的诚实边界**：限速只加在 WSL 的 `eth0` 出口（＝上传方向），
而且 `eth0` 是**公共出口**——严格说这违反"限速只匹配实验数据流"这条
（计划书 §5 原话）。实测期间没有别的 WSL 出网流量（k3s 的三个 worker Pod 空载、
没有 SSH、没有状态采集），所以这批数字可用；但**写正文时必须声明这条偏差**，
并且在正式跨云实验里把限速加到专用隧道接口上。

## 5. 对照臂：老协议（`--fake-transfer`）到底差在哪 —— `transfer_20261006T030058Z`

同一条被 `tc` 限到 25 Mbit 的 veth，同一个 worker，只把客户端与 worker 都切回
"按带宽睡眠"的老行为（worker 用 `--bandwidth-mbps 25`，睡眠时长 = 8 MB ÷ 25 Mbit/s ≈ 2.56 s）：

| 检查 | 真实字节收发 | 老协议（睡眠） |
|---|---|---|
| `overlimits` 增量 | +11201 / +11231 | **+0** ← 线上一个批量数据包都没有 |
| 上传吞吐 | 24.099 Mbit/s | n/a（没有载荷字节，吞吐一词不成立） |
| 1 路 vs 3 路（每请求端到端） | 2.805 s → 6.929 s（**2.47×**） | 2.561 s → 2.562 s（**1.00×**） |
| 网卡计数器 / 应用层字节 | 1.0459× | 无从对比（应用层没有发字节） |
| 字节一致性 | 逐字节相等 | 不适用（没有载荷） |

**一句话**：老协议的"带宽"是一个**与并发无关的睡眠时间**——3 个请求同时来，各自睡各自的，
互不拖慢；而且整条链路一个字节都没被它占用。所以老协议**结构上不可能**表达
"多个请求共用一条出口、彼此瓜分带宽"这件事，而那正是本课题要研究的机制。
这就是它必须被换掉的根本原因，也是 Threats to Validity 里要写的那句
"应用层模拟 vs 真实内核限速差多少"的定量答案。

## 6. 没跑通 / 受限的地方（照实写）

| # | 事项 | 状态 | 说明 |
|---|---|---|---|
| 1 | 单机自足模式（`--role transfer` 不给 `--target`） | **A1/A1b 能过，A3/A4 必然 FAIL** | 回环流量不经 `veth`，没有真实队列。这是设计如此：这个模式用来确认软件正确性，不能用来过阶段 A |
| 2 | Windows 侧的网卡计数器与 `tc` | **拿不到** | Windows 没有 `/sys/class/net`、也没有 `tc`。所以 Windows 当客户端那一轮（`transfer_20261006T030624Z`）的 A3/A5 只能记 n/a，A4 FAIL |
| 3 | `iperf3` 的双重确认 | **只在路径 1 做了，而且只在 Linux 侧** | Windows 侧没有 `iperf3`（装它要额外下载与授权），路径 2 没有第三方工具交叉验证，只有应用自身测量 |
| 4 | 跨机（真两台物理机）、跨云、RDMA | **完全没做** | 本机只有一台物理机。这条路径只能证明"内核 `tc` 整形 + 真实字节收发"这套机制是对的，**不能**说成跨机或生产级网络 |
| 5 | `tc` 只加在两块**新建的**虚拟网卡上（路径 1） | 符合计划书要求 | 路径 1 不碰 `eth0`、不碰 k3s 的 `cni*`/flannel，所以 SSH、集群管理、状态采集都没被限速。**路径 2 是例外**，见 §4 |
| 6 | k3s 集群在测试期间是开着的 | 已确认无干扰 | 三个 worker Pod 空载、无客户端打请求；它们走 `cni0`/flannel 虚拟网卡，与路径 1 的 `vethB` 是不同设备、不同命名空间 |
| 7 | 200 MB 档在 25 Mbit 限速下很慢 | 用时 133.8 s | 单程 200 MB @25 Mbit = 64 s。要跑全档就得接受这个时间；急用可把 `--sizes-mb` 收窄 |

### 过程中真踩到、并且已经修掉的坑

| # | 现象 | 真正原因 | 处置 |
|---|---|---|---|
| 1 | 路径 2 第一轮三个档位全部报 `RemoteDisconnected: Remote end closed connection without response`，看起来像防火墙拦了 | **Windows 那台机器的主机名是中文**（"青山"），worker 把它塞进 `X-Server-Node` 响应头，而 HTTP 头只能 `latin-1` → 服务端 `send_header` 抛 `UnicodeEncodeError`，**客户端只看到"对方没回话就断连"**，真错误只在服务端 stderr 里 | 新增 `header_safe()`，非 ASCII 用 `backslashreplace` 转义。坏记录 `transfer_20261006T030128Z` **按 append-only 保留**，它本身就是这个坑的证据 |
| 2 | 对照臂的"A2 下传吞吐"报了 48.773 Mbit/s 并判 FAIL | 老协议的响应体只有一段 JSON（几十字节），除以极短时长算出了**虚假吞吐** | `down_thr_mbps()` 在 `mode == "fake"` 或请求失败时返回 NaN；坏记录 `transfer_20261006T030039Z` 同样保留 |
| 3 | "四段之和 − 端到端"是**负数**（−0.0006 s） | 第一段只算了纯 `connect()`，漏掉 `putrequest/putheader/endheaders` 那段组头时间 | 第一段改成 `t_pre_send_s`（＝建连 + 组请求头），四段现在无缝无重叠，残差精确为 0 |
| 4 | 命令之间隔超过一分钟，`ip netns exec hostB ...` 报 `Cannot open network namespace "hostB"` | WSL2 空闲约 60 s 自动关机，netns/veth/tc 规则**不跨关机保留**（`MULTIHOST.md` §1.2 第 2 条） | 跑之前先挂一个 `wsl -d Ubuntu -u root -- sleep 7200` 保活会话 |
| 5 | `modprobe sch_netem` 报失败 | 这些 qdisc 编译进内核了，不做成模块 | 不用管；判据是 `tc qdisc add` 成功 + 实测吞吐 ≈ 设定值 |

## 7. 复现命令（照抄即可）

```bash
# ── 准备：把 WSL 挂住，否则 netns/veth/tc 会被空闲关机清掉 ──
wsl -d Ubuntu -u root -- sleep 7200 &      # 另开一个终端跑，别关

# ── 路径 1：两台"主机" + 双向 25 Mbit 内核限速 ──
wsl -d Ubuntu -u root -- bash /mnt/e/代码项目文件/论文/sim/k8s_test/setup_netns_tc.sh up 25

# 服务端放在 root 命名空间
wsl -d Ubuntu -u root -- bash -lc 'cd /mnt/e/代码项目文件/论文/sim && \
  python3 k8s_test/measure_system.py worker --bind 10.250.0.1 --port 9201 --compute 1e6 &'

# 验证电池放进 hostB（只有那里看得见被整形的 vethB）
wsl -d Ubuntu -u root -- ip netns exec hostB bash -lc 'cd /mnt/e/代码项目文件/论文/sim && \
  python3 k8s_test/measure_system.py transfer \
    --target 10.250.0.1:9201 --iface vethB --tc-rate-mbps 25 --shaped-direction both \
    --sizes-mb 0.5 8 200 --rate-test-mb 8 --rate-test-concurrency 3'

# ── 对照臂：老协议 ──
#   服务端加 --bandwidth-mbps 25，客户端加 --fake-transfer，其余完全一样

# ── 收尾 ──
wsl -d Ubuntu -u root -- bash /mnt/e/代码项目文件/论文/sim/k8s_test/setup_netns_tc.sh down

# ── 独立工具交叉确认 ──
wsl -d Ubuntu -u root -- bash -lc '
  iperf3 -s -B 10.250.0.1 -p 5201 -1 &
  sleep 1
  ip netns exec hostB iperf3 -c 10.250.0.1 -p 5201 -t 8 -f m'
```

## 8. 这些数字能用在哪、不能用在哪

**能用**：
- 证明"网络代价现在由**内核整形**产生，不是应用层睡眠"——有 `overlimits` 计数、`iperf3` 与
  应用自身双重确认、以及"去掉 `tc` 后吞吐高三到四个数量级"的对照。
- 证明"字节数、阶段时间、网卡计数器三本账对得上"——这是后面跨云实验做计费与对账的基础。
- 证明"并发传输会互相瓜分同一条出口"这个机制在真实内核队列里成立（2.3–3.0×）。

**不能用**：
- 不能说成"跨机"或"生产级网络"：路径 1 是同一台机器上的两个网络命名空间、经 `veth` 相连；
  路径 2 是一台物理机上的两套网络栈、经 Hyper-V 虚拟网卡相连。两者都**不是**机架间网络。
- 不能引用成"云间带宽/时延"的任何数值：`tc` 的 25 Mbit 是我们自己设的，
  25 Mbit ≠ 任何云厂商的实际链路能力。
- 不能把路径 1 的 4.6% 网卡开销比当作通用常数（见 §3.6）。
- 不能用于"状态年龄"相关结论：阶段 A 完全不涉及调度器与状态观测。
