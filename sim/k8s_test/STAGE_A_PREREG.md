## 2. 事先固定的比较口径（**主口径**）

**主口径 = 自研工具读数 对 同一会话 `iperf3` 的「发送端」读数。容差 ±5%。**

**为什么是这三个选择（理由全部来自第 1 段之前就已存在的信息，不是从本轮数据里挑的）：**

1. **为什么对"发送端"而不是"接收端"**：自研工具测的是**客户端发送窗口**内的字节数与耗时，
   与 `iperf3` 的发送端是**同一个记账边界**（数据交给内核就记账）。接收端统计的是"最后一个包真正到达"，
   含尾部排空，是另一个边界。**同一口径才可比。**
2. **为什么是 ±5% 而不是 ±2%**：第 1 段之前已有两次同会话实测，
   自研工具与 `iperf3` 发送端的差在 **2–4 个百分点**（5.721 vs 5.909；另一批 5.406 vs 6.151 属跨会话比较，已作废）。
   另外上传链路的**不限速基线本身波动达 8.5 倍**（同一轮内在 3.85–32.73 Mbit/s 之间）。
   **±2% 已经低于这台机器在这条公网路径上的测量分辨力**，把它当门槛等于让判据随机通过或失败。
3. **为什么还必须同时报"对接收端"和"≤2% 的通过率"**：主口径是**事先选定**的一种解释，
   另外两种口径要**照实并列**，供审稿人换角度复核。**不得只报主口径。**

# 附录：测速口径更正（**2026-10-07 01:2x，北京时间；在第 3 段开跑之前写定**）

## A.1 错在哪

上面 §2 声称："自研工具测的是**客户端发送窗口**，与 `iperf3` 的**发送端**是同一个记账边界"。

**这句话与代码不符。** 实际实现见 `sim/k8s_test/measure_system.py:1090`：

```python
def up_thr_mbps(r: dict) -> float:
    """上传方向的吞吐（Mbit/s）——**以服务端收到的字节数除以服务端收到它的耗时**。
    【为什么不用客户端发完的时刻】客户端 sendall 返回只表示数据进了内核发送缓冲，
    在被限速的链路上这个时刻远早于"对面真的收完"；用它会**系统性高估**吞吐。"""
    d = _nanf(r.get("srv_recv_s")); n = r.get("srv_recv_bytes") or 0
    return n * 8 / 1e6 / d if d and d > 0 else float("nan")
```

即：自研工具的上传吞吐是**接收端口径**（服务端收到的字节 ÷ 服务端收它的耗时），
**不是**发送端口径。下传方向（`down_thr_mbps`）同理，取的是**客户端收到**的字节与耗时，同样是接收端口径。

## A.2 更正后的口径安排

| 角色 | 口径 |
|---|---|
| **主交叉核对** | 自研工具（**接收端**）↔ `iperf3` 的**接收端**读数（`sum_received`） |
| **并列报告（不取消）** | 自研工具（接收端）↔ `iperf3` 的**发送端**读数（`sum_sent`） |
| **容差** | 仍为 **±5%**（§2 的理由不变：链接波动本身就有 2.5%~11% 量级） |
| **绝对真值** | **两个工具都不是真值。** 它们只是两个独立实现的边界不同的估计，两者一致只说明"没有实现错误"，不说明"这就是物理真值" |

## B.0 两条必须先说清的定性

### （1）前 40 轮是"前期试跑"，不是本规则下的确认结果

**95% 这个门槛是看过前 40 轮结果之后才形成的。** 把它说成"对这 40 轮事先预注册的门槛"是**循环论证**。因此：

- 前 40 轮（第 1、2、3 时段）**全部保留、单独报告**，明确标注为**前期试跑（pilot）**；
- **第 4 时段是新规则下的确认（confirmation）**；
- 预注册的目的之一，就是让读者分清**哪些分析是看数据之前定好的**、**哪些是看过数据之后形成的**。

### （2）95% 是工程放行线，不是统计证明

**它不是"真实长期成功率 ≥ 95%"的证明。** 40 轮且集中在少数时段，支撑不起这么强的说法。

**小样本比例必须给精确区间**（Clopper–Pearson 或 Wilson），**不能只报点值**。
正文里报通过率时，要同时给区间与样本量。
